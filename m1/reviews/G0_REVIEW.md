### Numbered Findings

#### Finding G0-1 (P1 must-fix)
- **Proposal Section**: §2 (Storage placement and consistency) / §6 (Action permissions required for M1) / §7 (Enforcement inventory — Tasks & Claims)
- **Problem**: Synchronization window race during `task.claim`. In [claims.ts#L112-L160](file:///home/box/engineering-workspace/worktrees/switchboard-m1/worker/src/claims.ts#L112-L160), `claim()` executes `await this.host.tasks.ensureSynced()` at line 113 *before* entering the synchronous SQL mutation block (lines 116–147). `ensureSynced()` performs an asynchronous GitHub API call to reconcile issues, which routinely takes hundreds of milliseconds to multiple seconds. If the Channel DO acquires the 2-second authorization permit at route entry ([index.ts#L275](file:///home/box/engineering-workspace/worktrees/switchboard-m1/worker/src/index.ts#L275) or [claims-api.ts#L71](file:///home/box/engineering-workspace/worktrees/switchboard-m1/worker/src/claims-api.ts#L71)), the permit is at severe risk of expiring before `this.host.tasks.write()` commits at line 140, resulting in spurious 403/503 refusals. Conversely, checking a permit only at route entry with an unverified commit violates the linearizability guarantee against grant revocation.
- **Evidence**: [claims.ts#L112-L160](file:///home/box/engineering-workspace/worktrees/switchboard-m1/worker/src/claims.ts#L112-L160); [tasks.ts#L214-L223](file:///home/box/engineering-workspace/worktrees/switchboard-m1/worker/src/tasks.ts#L214-L223); [M1_ARCHITECTURE_PROPOSAL.md#L38-L41](file:///home/box/engineering-workspace/worktrees/_agy_inputs/M1-G0/M1_ARCHITECTURE_PROPOSAL.md#L38-L41).
- **Exact Correction**: Explicitly specify that for `task.claim` (and `task.update` during `finish`), `ensureSynced()` must resolve *prior* to requesting the 2-second authorization permit from the `Organization` DO. The permit acquisition RPC must happen immediately after synchronization completes, and must be validated and consumed synchronously within the same tick that writes the claim and audit record to `ctx.storage.sql` without intervening `await` expressions.

#### Finding G0-2 (P1 must-fix)
- **Proposal Section**: §2 (Storage placement and consistency — Revocation fencing) / §8 (Open-stream revalidation)
- **Problem**: Unbounded revocation wait on slow or hibernating Channel DOs. §2 states: *"Revocation returns completed only after affected Channels acknowledge fencing or all pre-revocation permits expire."* However, when an Organization DO pushes invalidation to linked Channel DOs via Cloudflare Durable Object RPC, an unreachable, partitioned, or cold-starting Channel DO could block the Organization DO indefinitely if the RPC call lacks an explicit timeout.
- **Evidence**: [M1_ARCHITECTURE_PROPOSAL.md#L40](file:///home/box/engineering-workspace/worktrees/_agy_inputs/M1-G0/M1_ARCHITECTURE_PROPOSAL.md#L40); [relay.ts#L396-L400](file:///home/box/engineering-workspace/worktrees/switchboard-m1/worker/src/relay/relay.ts#L396-L400) (codebase standard for bounding asynchronous DO events).
- **Exact Correction**: Mandate an explicit timeout on the Organization DO's invalidation push to linked Channels capped at ≤2,000 ms (matching the maximum 2-second permit lifetime) via `AbortSignal.timeout(2000)`. If any linked Channel fails to acknowledge within 2,000 ms, the Organization DO must proceed to mark the revocation completed, since all pre-revocation permits are guaranteed expired by wall-clock time bounds.

Cloudflare Durable Object alarms (`setAlarm`) are best-effort background timers subject to platform scheduling jitter and wakeup latency, especially during hibernation, and cannot guarantee millisecond-level precision.
- **Evidence**: [M1_ARCHITECTURE_PROPOSAL.md#L138](file:///home/box/engineering-workspace/worktrees/_agy_inputs/M1-G0/M1_ARCHITECTURE_PROPOSAL.md#L138); Cloudflare DO documentation.
- **Exact Correction**: Explicitly document that the 5-second stream revocation guarantee is enforced *synchronously at the send boundary* on each message or frame dispatch (`if (Date.now() > wsAttachment.leaseExpiresAt) return drop()`), rather than relying on the alarm callback to wake and close the socket. The DO alarm must be specified strictly as a background reclamation sweep for idle connections.

### Agreements (Design Choices Independently Endorsed)

1. **Storage Architecture (Organization DO + IdentityDirectory DO)**: Retaining the existing `Channel` Durable Object storage and SQLite engine while adding a dedicated `Organization` Durable Object per organization is sound. It avoids introducing D1 or external relational databases, preserves existing Miniflare test topologies ([vitest.config.ts#L59-L66](file:///home/box/engineering-workspace/worktrees/switchboard-m1/worker/vitest.config.ts#L59-L66)), and ensures atomic local policy transactions without distributed two-phase commit overhead.
2. **Two-Second Permits & Linearized Fencing**: Using 2-second server-only permits consumed synchronously by the Channel DO provides a concrete, provable linearization boundary between policy decisions in the `Organization` DO and mutations in the `Channel` DO, preventing distributed deadlocks.
3. **Four-Way Policy Intersection & Server-Side Enforcement**: Defining effective agent permissions as `org ceiling ∩ workspace policy ∩ agent grant ∩ current sponsor delegable authority` evaluated on every decision ([M1_ARCHITECTURE_PROPOSAL.md#L74-L75](file:///home/box/engineering-workspace/worktrees/_agy_inputs/M1-G0/M1_ARCHITECTURE_PROPOSAL.md#L74-L75)) completely eliminates prompt-based or self-asserted authority escalation.
4. **Stable Principals vs Ephemeral Scoped Executions**: Maintaining stable `AgentPrincipal` identities while issuing distinct `AgentExecution` tokens with random 256-bit secrets hashed with SHA-256 at rest ([M1_ARCHITECTURE_PROPOSAL.md#L56-L68](file:///home/box/engineering-workspace/worktrees/_agy_inputs/M1-G0/M1_ARCHITECTURE_PROPOSAL.md#L56-L68)) satisfies Invariants 4 and 5, avoiding perpetual grants or token reuse across workspaces.
5. **Two-Phase Channel ↔ Workspace Binding**: Enforcing simultaneous verified GitHub repo admin authority ([access.ts#L156-L166](file:///home/box/engineering-workspace/worktrees/switchboard-m1/worker/src/access.ts#L156-L166); [rest.ts#L117-L127](file:///home/box/engineering-workspace/worktrees/switchboard-m1/worker/src/github/rest.ts#L117-L127)) and `workspace.manage` in the destination organization ([M1_ARCHITECTURE_PROPOSAL.md#L144-L149](file:///home/box/engineering-workspace/worktrees/_agy_inputs/M1-G0/M1_ARCHITECTURE_PROPOSAL.md#L144-L149)) prevents cross-organization hijack or unilateral channel reassignment.
6. **Strict Preservation of Four CLI Adapters & Legacy Channels**: Keeping unlinked repository Channels fully backward-compatible with original semantics and leaving adapter code untouched ([M1_ARCHITECTURE_PROPOSAL.md#L60](file:///home/box/engineering-workspace/worktrees/_agy_inputs/M1-G0/M1_ARCHITECTURE_PROPOSAL.md#L60), [L150-L153](file:///home/box/engineering-workspace/worktrees/_agy_inputs/M1-G0/M1_ARCHITECTURE_PROPOSAL.md#L150-L153)) directly satisfies Invariant 1.
7. **Exclusion of Central LLM Orchestrator & Out-of-Scope Milestone 2 Features**: Resisting speculative central LLM orchestration, remote write MCP, or generic work objects maintains product focus strictly on the authorization foundation mandated by [SPEC.md#L122-L130](file:///home/box/engineering-workspace/worktrees/_agy_inputs/M1-G0/SPEC.md#L122-L130).
