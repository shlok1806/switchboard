# A Person is a GitHub account; one Channel per repo; one GitHub App for sign-in and writes

A Person is a GitHub account, and their GitHub login is their name everywhere, the first part of every Agent ID they run (`shlok1806/claude/7f3a`). The Dashboard signs in with GitHub's web flow and the CLI (`switchboard login`) with its device flow, both through the one Switchboard GitHub App. The GitHub user token is used once, to learn the login, and then dropped: the Worker hands out its own session instead, an HMAC-signed token (SESSION_SECRET) that the Dashboard keeps in an HttpOnly, Secure, SameSite=Lax cookie and the CLI in its config file. So the App's expiring user tokens never need refreshing.

There is one Channel per GitHub repo, a Durable Object named by `owner/repo` (lowercased). Its API lives at `/r/<owner>/<repo>/api/...`, its Dashboard at `/<owner>/<repo>`, sign-in at `/auth/...`, and the App's single webhook at `/api/github/webhook`, which routes each delivery to the Channel of its `repository.full_name`. The `/r/` prefix keeps a repo named `api` or `auth` from colliding with the Worker's own routes. While testing, the ALLOWED_REPOS var lists the only repos that may have a Channel, so a stranger cannot open Channels for other repos.

Membership is write access to the repo, read with the App's installation token from `GET /repos/{owner}/{repo}/collaborators/{login}/permission` (write, maintain or admin). It is checked with GitHub at sign-in and re-checked at most every five minutes per Person, cached in the Channel. Open streams are re-checked on the same schedule and closed when access is gone. If GitHub cannot be reached, a Person let in within the last hour stays in; nobody new gets in. There is no invite list of our own: the repo's collaborators are the list.

Each Agent acts with its own token. `switchboard run` registers the Agent with the Person's session and gets back an Agent token bound to that one Agent ID; only its SHA-256 is stored. The token can read the Channel, post the Agent's own Events (hooks, the proxy, tool calls, Updates), claim, release and finish Tasks for itself, and heartbeat and end itself. It cannot send Directives, create Tasks, take over Claims, change Proxy modes, register Agents or act for any other Agent; the Worker refuses those with 403 before the call reaches the Channel's own rules. A WebSocket opened with an Agent token is that Agent's, and only it may carry the Agent's Hook and Proxy Events. The token is revoked when the Agent goes Gone, and its sockets are closed; resuming registers again and gets a new one. This keeps a prompt-injected Agent (ADR 0005) from speaking as its Person.

All GitHub writes go through the App's installation token, cached until five minutes before it expires, so they show as `switchboard[bot]` with the Person and Agent named in the text. The holder's Person is the Issue's assignee, so GitHub still notifies the old and new assignee. Each Issue has one status comment, edited in place (issue #2): holder and Agent, Steps done, the last Update and a short history. Its ID is stored per Task, and a comment someone deleted is posted again at the next change.

We rejected a shared join secret with self-picked names (the interim setup): anyone with the secret could be anyone. We rejected a separate invite system, because the repo already says who may push to it. We rejected giving Agents the Person's session, because then any Agent could send Directives. We rejected a personal access token for writes, because every write would show as the token's owner.

A dev-only fake sign-in (`/auth/dev/...`) exists for `wrangler dev` and the tests. It answers only when the DEV_FAKE_GITHUB var is "true" and the request came to localhost, which a deployed Worker never is. Until the App's secrets and SESSION_SECRET are set, the Worker still deploys and runs, and sign-in says "GitHub App not configured".
