## Smallest extensions

All design entries in this section are [RECOMMENDATION]. Status refers to the present target capability, not proposed code. Changes should be additive and preserve the current GitHub coding workflow until a caller deliberately selects another capability/provider.

### 1. Explicit agent kinds and a small coordination SDK

Current status: **Partially implemented**. Add an agent kind and declared capabilities independent of CLI labels, plus wire-version negotiation. Extract registration, Task reads/claims, Updates, notes, heartbeat and subscriptions into a small HTTP/WS client. Keep local git/PTY helpers optional. Extend `parseRegister`, shared `Agent`, and `ChannelClient` (`worker/src/agents-api.ts:142-232`; `shared/src/domain.ts:43-103`; `cli/src/channel-client.ts:224-259`, `:276-324`).

Dependencies: agree on backwards-compatible defaults and capability semantics; initial provisioning can remain Person-backed. Risk: legacy clients may assume every Agent has a terminal or a supported resume format. Test strategy: old registrations unchanged; new HTTP-only service without cwd/PTY; unknown optional capability handling; token/actor binding; disconnect/backoff and Queue downgrade. Preserve four existing adapters, collision handling, self-only actions and existing token transition (`worker/src/agents.ts:252-261`; `worker/src/index.ts:301-311`).

### 2. Stable principals with scoped execution credentials

Current status: **Not implemented** for the independent company/vendor actor (N2). Introduce stable principal IDs for organizations, employees and sponsored external vendors, distinct from transient execution/session IDs. Add credential issuance, scope, expiry, revocation and sponsorship records; retain Person attribution and legacy sessions. Extend `Access.admit/issueAgentToken`, `AgentRoster.register` and the existing grant lifecycle rather than replacing them (`worker/src/access.ts:92-114`, `:178-194`; `worker/src/agents.ts:252-352`; `worker/src/mcp/oauth.ts:482-517`).

Dependencies: SDK identity contract and explicit founder decisions on vendor sponsorship/revocation. Risk: widening a session token into persistent authority, confused attribution or grants surviving offboarding. Test strategy: cross-organization isolation, vendor expiry, sponsor removal, revoked/rotated credentials, persistent principal with multiple concurrent executions, old Person/session registration. Preserve Gone revocation of execution credentials and separate read-only connector credentials (`worker/src/access.ts:192-194`; `worker/src/mcp/server.ts:74-85`). Do not silently reinterpret existing tokens as organization-wide grants.

### 3. One policy decision boundary for permitted work

Current status: **Partially implemented** overall; the organizational mandate engine is **Not implemented** (N4). Add explicit policy decisions for visibility, claim, creation, review, data export and delegation, enforced at common API admission and mutation boundaries. Let callers choose among permitted Tasks. Extend `handleChannel`, `Access.checkMember`, `Claims.claim/held`, and the existing subtree rules (`worker/src/index.ts:272-324`; `worker/src/access.ts:117-148`; `worker/src/claims.ts:112-147`, `:263-283`; `worker/src/channel.ts:993-1035`).

Dependencies: principal/scopes model, organizational ownership and a policy revision model. Risk: a new route bypassing policy, overly broad discovery or cached access surviving a policy change. Test strategy: decision tables across principal/action/resource, read/write parity, fail-closed errors, revocation during open streams, delegation ceilings, explicit reasons. Preserve atomic claim check/write, Person-owned sessions, existing lead subtrees and local Host ceilings. Central policy must not imply that centrally advertised Host roots can widen the machine's local permissions (`cli/src/host/check.ts:98-117`).

### 4. Reliable mutation and delivery contracts

Current status: **Partially implemented** (N6). Add scoped request keys with bounded result replay; retain deliveries until explicit receipt ACK; compare Task holder/branch or revision before applying post-await PR results. Extend `Relay.takeDeliveries/acknowledge`, `Channel.withNextTurn/postUpdate`, and `Branches.finish` (`worker/src/relay/relay.ts:267-277`; `worker/src/channel.ts:972-982`, `:1172-1181`; `worker/src/branches.ts:112-129`). Clarify receipt versus model consumption; receipt should not promise exactly-once reasoning.

Dependencies: SDK persistence/ACK capability and caller identity scoping; can begin with legacy identities before the organizational model. Risk: duplicate handling, unbounded retained queues, keys reused for changed payloads, or an ACK sent before durable local receipt. Test strategy: lost POST/heartbeat responses, repeated keys with same/different payloads, crash before/after receipt, out-of-order ACKs, release/reclaim during PR creation, expired replay retention. Preserve current WS ACKs, same-holder no-op, signed webhook deduplication and sequential PR reuse (`worker/src/claims.ts:126-127`; `worker/src/branches.ts:161-205`; proving retry assertions `worker/test/branches.test.ts:211-214`).

### 5. Scoped agent proposals, creation and relation writes

### 6. Additive work references, completion and independent review

Current status: **Blocked by a current architectural constraint** for non-GitHub/non-PR completion; generic acceptance is **Not implemented** (N5). ### 7. Explicit routing/data retention policy

## Ordered plan by dependency and risk

All steps are [RECOMMENDATION]; this is a design sequence, not authorization to implement or deploy.

1. Specify compatibility and receipt semantics; isolate the SDK and explicit capabilities. In parallel design, harden retry/ACK and PR post-await checks against the concrete current risks. These fit existing identity and reduce integration risk (extensions 1/4; `cli/src/channel-client.ts:224-259`; `worker/src/relay/relay.ts:267-277`; `worker/src/branches.ts:112-129`).
2. Introduce stable principals and scoped executions, then enforce shared policy with legacy defaults preserved. This is the highest authority risk and a prerequisite for expanding vendor writes (extensions 2/3; `worker/src/access.ts:92-148`; `worker/src/index.ts:272-324`).
3. Add policy-governed follow-on proposals/creation and independent review on existing Issue Tasks. This unlocks organizational collaboration before migrating Task identity (extensions 5/6; `worker/src/tasks.ts:181-189`; `worker/src/branches.ts:89-153`).
4. Add non-PR completion and evidence revisions; evaluate provider-independent references and non-repo Channels only after deciding ownership/membership rules. This carries the greatest migration risk (extension 6; `worker/src/tasks.ts:131-135`; `worker/src/index.ts:63-65`).
5. Make external-model/data retention policy explicit before onboarding agents with restricted data. Add A2A/scoped write MCP only for proven consumer needs (extensions 7/8; `worker/src/relay/jev.ts:66-85`; `worker/src/mcp/server.ts:94-108`).
