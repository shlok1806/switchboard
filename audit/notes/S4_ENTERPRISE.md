## A. Can an independently deployed agent connect today?

**Custom HTTP participation: Partially implemented.** [INFERENCE] A custom program can implement the wire protocol without running a coding CLI or the official wrapper, provided a GitHub-backed Person provisions it and it presents one of the supported CLI labels. Registration validates an enum and session-ID syntax, rather than attesting a running CLI (`parseRegister`, `worker/src/agents-api.ts:142-175`); CLI names are only `claude-code`, `codex`, `cursor`, `gemini` (`shared/src/domain.ts:25-26`; `CLI_SHORT_NAMES`, `shared/src/agents.ts:14-21`). This is protocol reuse under an inaccurate identity label, not first-class arbitrary-agent support.

[FACT-CODE] A minimal integration can use the following sequence:

1. Obtain a Person session through GitHub web flow (`GET /auth/github/start`, `GET /auth/github/callback`) or device flow (`POST /auth/device/code`, `POST /auth/device/token`; cookie alternative `/auth/device/session`), dispatched by `handleAuthRoute`, `worker/src/auth-api.ts:94-122`. `Access.checkMember` requires GitHub write/maintain/admin access through `canWrite`, `worker/src/access.ts:117-148`, `worker/src/github/types.ts:72-76`.
2. With that Person bearer, `POST /r/<owner>/<repo>/api/agents`, JSON such as `{"cli":"codex","sessionId":"external-session-0001","interrupts":false}`. `parseRegister` defaults `resumed` false and `cwd` empty; Host, spawn, historyHost and predecessor are optional (`worker/src/agents-api.ts:171-232`). The returned token is a narrow Agent credential (`answer`, `:237-249`; `Access.issueAgentToken`, `worker/src/access.ts:178-189`). Agent tokens cannot register another Agent (`handleChannel`, `worker/src/index.ts:283-311`). Keep the provisioning Person credential outside the autonomous client.
3. Use Agent bearer HTTP to list Tasks/Agents, read Events, claim/release/complete steps, post Updates, write/read Memory and use other permitted content routes. The exact reusable interface families are in H; route admission is `handleChannel`, `worker/src/index.ts:283-337`. HTTP bearer is accepted directly; cookies and WS query tokens are alternatives (`readCredential`, `worker/src/auth.ts:82-114`). Heartbeat and end use `POST /api/agents/:id/heartbeat` and `/end` (`ChannelClient`, `cli/src/channel-client.ts:238-259`).
4. Optionally open `GET /r/<owner>/<repo>/api/stream?after=<seq>` with WS upgrade and bearer or `token` query. `handleStream` validates the cursor and binds authenticated identity, `worker/src/index.ts:165-182`; `Channel.fetch` sends backlog Events then roster before the live stream, `worker/src/channel.ts:1863-1875`. Polling HTTP and heartbeat handover can supply a simpler integration, subject to I's delivery-loss caveat (`Channel.withNextTurn`, `worker/src/channel.ts:966-982`).

**Basic Agent bearer participation: Implemented and verified.** [FACT-TEST] `worker/test/identity.test.ts:339-357`, “are issued when the Person's session registers an Agent, and act as that Agent”, asserts Update attribution, reads, heartbeat, claim and release. This is a protocol test using fixtures, not a deployed third-party agent test. **Actual arbitrary-agent interoperability: Implemented but unverified** for the above emulation; no real independently deployed client was exercised here (`parseRegister`, `worker/src/agents-api.ts:171-232`).

## C. Work abstraction and GitHub coupling

**GitHub Task mirror: Implemented and verified.** [DOC-ONLY] ADR 0007 specifies one Channel per repo and ADR 0001 specifies one Task per Issue (`docs/adr/0007-github-identity-one-channel-per-repo.md:3-7`; `docs/adr/0001-tasks-mirror-github-issues-with-field-ownership.md:3-7`). [FACT-CODE] The actual constraints are unambiguous: `channelOf` names the DO by repo (`worker/src/index.ts:63-65`); `channelRepo/allowedRepos` lowercases/filters configured repositories, with empty allow-list allowing any valid key (`worker/src/auth.ts:53-66`); deployment has three allowed repos (`worker/wrangler.jsonc:24-28`). `TaskNumber` means GitHub Issue number, `TaskStatus` is open/claimed/review/done (`shared/src/domain.ts:124-138`). `Tasks` stores rows under integer `number` PK, copies GitHub-owned title/body/labels/blockers/parent/subtasks/checklist/url, and creates new work by `gitHub.createIssue` (`worker/src/tasks.ts:86-110`, `:127-141`, `:181-189`). [FACT-TEST] “shows each open Issue as a Task, with Subtasks under their parent, Steps and blockers” asserts numbers, URL, parent, checklist and only open blockers (`worker/test/tasks.test.ts:101-154`). Its title is broader than “all historical Issues”: closed Issues never observed open are expressly absent (`:128-129`).

**Non-coding work stored in GitHub Issues: Partially implemented.** [INFERENCE] Text, labels, Steps, Memory, Updates and claims can represent research/operations work without editing source; raw HTTP claim simply records a hold (`Tasks.mirroredFields`, `worker/src/tasks.ts:96-110`; `Claims.claim`, `worker/src/claims.ts:112-147`). However, local `claim_task` creates a branch/worktree, and completion through `finish_task` pushes a branch and opens a closing PR (`SwitchboardTools`, `cli/src/mcp-server.ts:502-525`, `:582-593`). The server also requires `task/<number>-<slug>` and a branch for finish (`Branches.record/finish`, `worker/src/branches.ts:56-74`, `:89-129`). These behaviours would be surprising for non-coding work. GitHub-side close is already a synchronization input (`Tasks.webhook`, `worker/src/tasks.ts:192-197`), but is not a generic Agent-authorized completion endpoint.

**Repo-independent work backend: Blocked by a current architectural constraint.** [FACT-CODE] The constraint is shared identity/storage/routing and field ownership, not merely a UI label: integer issue keys (`worker/src/tasks.ts:133-135`), issue-number URL matching (`worker/src/tasks-api.ts:17-18`), Updates validate a positive GitHub issue number (`worker/src/index.ts:151-153`), per-repo DO routing (`:63-65`), GitHub-dependent initial sync (`Tasks.ensureSynced/withGitHub`, `worker/src/tasks.ts:213-228`) and production GitHub membership (`worker/src/access.ts:128-139`). Dependencies are filtered to this repo (`worker/src/github/webhook.ts:64-66`; `GitHub` relationship API, `worker/src/github/types.ts:87-92`). [RECOMMENDATION] Keep the GitHub provider and add optional external work references, a completion strategy and eventually an independent Channel key; migrate through additive fields/provider boundaries, preserving issue-number clients and mirror ownership (`worker/src/tasks.ts:95-110`, `:181-189`; `worker/src/branches.ts:89-153`). No need to invent fake issues/PRs as an enterprise abstraction.

[FACT-CODE] `Relay.consider` first excludes undeliverable/raw content; `relay` drops no-overlap/unaddressed Events by rule, otherwise asks Jev (`worker/src/relay/relay.ts:254-263`, `:287-305`). `HttpJev.verdict` sends bounded structured state and drop/queue/interrupt question to TypeSafe's external HTTP endpoint, model `jev-latest` (`worker/src/relay/jev.ts:22-38`, `:66-85`; state `worker/src/relay/relay.ts:496-529`).
